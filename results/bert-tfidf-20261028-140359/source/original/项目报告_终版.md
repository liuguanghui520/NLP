## 摘要

在 ChnSentiCorp（携程酒店评论，7,766 条）二分类情感任务上，本项目在同一份数据划分、同一套
指标口径下并排比较了四条路线：字符 n-gram TF-IDF + LogisticRegression 基线、MacBERT-base
全参微调、Qwen3-1.7B 零/少样本提示、Qwen3-1.7B + LoRA 轻量微调。测试集 777 条
（负面 245 / 正面 532），与训练集严格不重叠。最优路线是 MacBERT 全参（lr_1e5），测试集 Accuracy
0.9228、Weighted F1 0.9229；大模型提示臂无需训练即可达到 Weighted F1
【待补：P_BEST_WF1】，说明「提示」不是「凑合用」的方案；LoRA 只训练了 【待补：LORA_PARAMS】 个参数
（【待补：LORA_PCT】%）却把结果推到 【待补：LORA_WF1】。结论是：在本任务这种中等规模、标签边界模糊的
中文情感语料上，按 weighted F1 排序是 **【待补：总体排序】**
（【待补：各路线 weighted F1】），最高与最低相差 【待补：最高与最低差距】 个百分点，【待补：差距评价】；
但训练成本从「0 参数」到「102,269,186 参数」差了好几个数量级——
**准确率的差距远小于算力与成本的差距**，
提示工程在「不碰权重、零训练成本」的约束下具备真实可用性。

## ① 问题定义与背景

### 1.1 要解决什么问题

给定一条中文酒店评论，判断它的**整体情感倾向**是负面（label=0）还是正面（label=1）。
给谁用：OTA / 酒店集团的评论监控与舆情看板，以及需要自动过一遍海量评论初筛的运营团队。

### 1.2 成功判据（可检验，不写"效果好"）

本项目把判据拆成三层，全部可在测试集上直接测量：

| 层级 | 判据 | 具体阈值/口径 | 为什么这么定 |
|---|---|---|---|
| 能力下限 | 非大模型基线要能跑通 | TF-IDF + LR 的 Accuracy ≥ 0.80 | 给"提示/微调"一个地板，低于这个数说明任务或特征本身有问题 |
| 主判据 | 各路线 Accuracy / Macro F1 / Weighted F1 | 同一测试集、同一套手写实现 | 跨路线可比；Macro F1 单独看小类（负面 245 条）有没有被牺牲 |
| 成本判据 | 提示臂的指令遵循率与延迟 | 指令遵循率 ≥ 90%，P95 延迟记录在案 | 提示臂最大的风险不是"准不准"而是"不听指令"，必须单独测 |

> **为什么同时报 Macro F1 和 Weighted F1**：本数据集类别不均衡（正 68.5% / 负 31.5%），
> 一个把所有样本都判成正面的模型 Accuracy 就有 0.685，但 Macro F1 只有 0.5。
> 本项目在冒烟测试阶段真实踩到过这个坑（见 §④ 坑 5），所以两个指标都必须报。

### 1.3 为什么值得做

- **业务价值**：人工过评论是典型的"高吞吐低单价"任务，情感判别是其中最容易自动化的一环。
- **学术/教学价值**：这个任务同时容纳了"传统特征工程""小模型全参微调""大模型提示"
  "大模型参数高效微调"四种范式，且规模足够小（一张 T4 就能全跑完），
  是一次能在课程作业里真正跑完的"提示 vs 微调"对照实验。

## ② 相关工作与方案选型

| 备选方案 | 优点 | 缺点 | 本项目是否采用 | 理由 |
|---|---|---|---|---|
| 词袋 / n-gram + 线性分类器 | 训练秒级、零 GPU、可解释、不易过拟合 | 捕捉不到长距离依赖和否定；上限低 | ✅ 作为**基线** | 任务书要求方向 C 必含"非大模型基线"；它同时给 BERT 提供下界对照 |
| 小模型全参微调（MacBERT-base） | 中文预训练、参数量适中、全参可塑性强、推理便宜 | 需要标数据 + GPU；本机 CPU 要 24~30 小时 | ✅ 作为**主路线** | 本组成员分工覆盖此模块；它代表"传统微调"的天花板参照 |
| 大模型零/少样本提示 | **零训练成本**、改提示词就能改行为、迭代快 | 指令遵循不稳、输出需解析、延迟高、可能不听话 | ✅ 作为**对照主线** | 方向 C 的核心命题就是"不训练能不能做" |
| 大模型 LoRA 微调 | 只训极小参数量、能注入领域知识、显存友好 | 秩/学习率等超参敏感；依赖 peft 生态 | ✅ 作为**对照主线** | 与提示臂共用同一底座，构成"提示 vs 微调"的严格同底座对比 |
| 纯 RAG / 检索增强 | 可溯源、适合知识型问答 | 本任务**没有外部知识库可检索**，检索不改变标签判别 | ❌ | 见下方说明 |

### 2.1 为什么不用 RAG

RAG 解决的是"**答案不在参数里**"的问题——需要外部文档、规章、数据库。本任务的标签判别
所需的知识**全部在任务本身**（"房间干净"、"服务员态度好"是正面词），
而这个领域知识恰好是**在预训练语料里出现得少、但可以被少量标注数据教会**的类型。
给一条 200 字的评论做检索，检索回来的多半是别的评论，对判这条评论没有增益。
本项目因此把 RAG 排除在方案之外，把算力预算全部投在"提示 vs 微调"的对比上。

### 2.2 为什么不用微调 / 为什么不用提示（互斥问题的正面回答）

- **为什么"不能只做微调"**：微调需要标注数据和算力。方向 C 关心的是"在给定约束下
  哪条路线更划算"，如果没有提示臂，结论只能是"微调很准"，无法回答"不训练行不行"。
  所以提示臂是**必做**的对照，不是可选项。
- **为什么"不能只做提示"**：提示臂的准确率受底座模型能力制约，且指令遵循率不保证。
  如果只报提示臂而不报微调，读者无法判断"是该换提示词还是该上微调"。
  所以微调臂（含传统基线、MacBERT 全参、LoRA）也是**必做**的。

### 2.3 关键设计决策：③④ 共用同一底座

Qwen3-1.7B 提示臂和 Qwen3-1.7B + LoRA 臂用的是**同一个底座模型、同一份训练/验证/测试划分、
同一套指标实现**，唯一区别是"怎么问"和"练不练"。
如果一个用 Qwen3、另一个用别的模型，任何差异都无法归因到"提示 vs 微调"本身。
这是本项目全部结论能成立的前提。

### 4.2 环境

| 路线 | 硬件 | Python | 关键依赖 | 耗时 |
|---|---|---|---|---|
| ① TF-IDF | 任意 CPU | 3.11.9 | scikit-learn 1.9.1 | ~6 秒 |
| ② MacBERT | **本机 CPU**（R5 5600H，6 核 12 线程，15.4 GB 内存，无独显） | 3.11.4 | torch 2.10.0+cpu | 全套（8 组 + 5 点曲线 + 对照）见 §4.5 |
| ③ 提示 | Kaggle T4 ×2 | 3.11.9 | transformers ≥ 4.51 | 约 25 min |
| ④ LoRA | Kaggle T4 ×2 | 3.11.9 | transformers ≥ 4.51, peft ≥ 0.13 | 约 50 min |

> **② 为什么在本机 CPU 上跑完，而不是上 Kaggle**：
> 本机没有 NVIDIA 显卡（只有 0.5 GB 的 AMD 核显），但 MacBERT-base 只有 1.02 亿参数，
> fp32 权重 + 梯度 + AdamW 两份动量合计约 1.6 GB，15.4 GB 内存完全装得下。
> 真正的问题不是"能不能装下"，而是"要跑多久"——见 §4.5 的提速。
> ③④ 两条 LLM 臂**本机不可行**：Qwen3-1.7B 的 fp32 权重约 6.8 GB，
> 加上 AdamW 动量约 13 GB，超过本机 15.4 GB 物理内存，因此这两条臂放 Kaggle。

### 4.3 遇到的具体问题与解决方式

这一节是本项目工作量最集中的部分，下面 8 条全部是实际卡住过、并且都能在
`src/README.md` 第 8 节和代码里对应到的问题。

| # | 现象 | 根因 | 解决方式 | 定位 |
|---|---|---|---|---|
| 1 | LoRA 训练 `loss=nan`，一步就发散 | LoRA 参数在 fp16 下，AdamW 的 `eps=1e-8` 在 fp16 里下溢成 0 → 除零 | 把所有 `requires_grad=True` 的参数 `.float()` 转 fp32；分类头输入也强制 fp32 | `qwen_lora.py` |
| 2 | Qwen3 分类结果几乎全错，但**不报错** | `Qwen3ForSequenceClassification` 用 `config.get_text_config().pad_token_id` 找最后一个非 pad 位做池化；Qwen3 的 config 是**扁平**的（没有 `text_config` 嵌套）且**不带** `pad_token_id`，与 tokenizer 的 151643 不一致时取错位置且静默通过 | 写递归 `set_pad()` 遍历 `text_config/sub_config/decoder` 三种可能的嵌套结构，把 `pad_token_id` 显式写进 config | `qwen_lora.py` |
| 3 | 提示臂输出是乱码 | 生成时用了右侧 padding，batch 内短句被 pad 截断 | `tok.padding_side = 'left'` | `qwen_prompt.py` |
| 4 | 提示臂先吐一大段"思考过程"再给答案 | Qwen3 默认开启 thinking 模式 | `apply_chat_template(..., enable_thinking=False)` | `qwen_prompt.py` |
| 5 | 冒烟时 Macro F1 假性掉到 0.5，Accuracy 却有 0.69 | 冒烟子集取了**前 N 条**，而数据按源文件顺序排列，前 N 条几乎全是正面（占 68.5%），模型全判正也能拿 0.685 | 冒烟子集改成**分层取样**（`stratified_first`） | `bert_full.py` |
| 6 | 三条路线的 F1 数字对不上 | BERT/LoRA 的 weighted F1 用了**训练集**的类别数做权重，而 sklearn 的 `average='weighted'` 用的是**测试集真实标签数** | 统一改成按测试集真实标签计数加权，并与 sklearn 交叉验证数值一致 | `bert_full.py`、`qwen_lora.py` |
| 7 | zip 传到 Kaggle 后解不开 | Windows `Compress-Archive` 生成的条目名用反斜杠 `\` | 改用 Python `zipfile` + `as_posix()` 重打包，条目名全为正斜杠 | `_pack_zip.py` |
| 8 | TF-IDF 主表和明细文件来自不同配置 | 3 组 n-gram 各跑各的，主表取最优但明细文件写死成了另一组 | 用 `FITTED` 字典保留每组拟合好的对象，主表和明细都取**验证集最优**的那一组 | `tfidf_baseline.py` |

### 4.4 工程细节

- **可复现性**：`random` / `np.random` / `torch`（含 `torch.cuda.manual_seed_all`）全部显式设种子；
  解码一律 greedy（`do_sample=False`），提示臂输出因此是确定的。
- **子集冻结**：少样本示例、延迟测试集、冒烟集的 ID 清单提前写进 JSON 写进数据包，
  三条臂共用同一份，**不随运行重抽**——否则提示臂可以"偷看"测试集挑例子。
- **GPU 适配**：`device_map={'': 0}`（单卡占满，多卡不并行）；开 gradient checkpointing 时
  必须同时 `enable_input_require_grads()`，否则 checkpoint 段没有梯度。
- **OOM 兜底**：LoRA 训练循环里 `except torch.cuda.OutOfMemoryError` 跳过该 batch 并继续，
  避免一条超长样本毁掉整轮 50 分钟的训练。

### 5.3 消融与参数对比

#### （1）TF-IDF 基线：n-gram 粒度与分词方式对比（回应任务书原理点 1）

同一份数据、同一个分类器（C=4.0 的逻辑回归），只改"怎么切词"，结果如下：

| 配置 | 切词方式 | 特征数 | val Acc | test Acc | Macro F1 | Weighted F1 |
|---|---|---|---|---|---|---|
| `char_1_3` | 字符 1—3 gram | 130,996 | 0.9021 | 0.8842 | 0.8610 | 0.8820 |
| `word_1_2` | **jieba 词级 1—2 gram** | 55,013 | 0.8943 | 0.8970 | 0.8783 | 0.8959 |

**结论（用本项目自己的数据回答原理点 1）**：

- **词表大小差了一倍多**：字符 1—3 gram 需要 130,996 维特征才能覆盖，
  jieba 词级只要 55,013 维——因为词级把"房间很大""服务态度好"这类
  完整语义单元当作一个特征，而字符级只能把汉字逐个和两两组合。
- **效果的方向和直觉相反**：词级在**测试集**上 Accuracy 高 +1.28 个百分点、
  负面类 F1 达到 0.8305（字符级是 0.8043），
  少数类的识别确实受益于完整的词——这说明**中文情感的关键信号落在词上**，
  "不好""很差""不干净"这类否定组合被字符级切碎了。
- **但词级在验证集上反而低 -0.78 个百分点**，所以本项目的主结果仍然取
  验证集最优的 `char_1_3`。这不是挑数据，而是**评测协议**：用测试集选模型等于拿答案做选择，
  属于典型的测试集泄漏。两种切法的验证集差距（不到 1 个百分点）本身也在噪声范围内
  （776 条样本上单个准确率的标准误约 1.1 个百分点），真正值得记住的是
  **"分词方式会改变少数类的表现"这个方向性结论**，而不是这 1 个百分点谁高谁低。

> 这条对照也解释了为什么 §4.1 里 TF-IDF 选字符 n-gram 作为主基线：
> 它不依赖外部分词器（`jieba` 是额外依赖，且中文分词本身有歧义），
> 在只有 6,210 条训练数据的小样本上更稳。**两者都报了，不藏。**

#### 主结果是怎么选出来的：**按验证集，不按测试集**

代表组 = 8 组里**验证集准确率最高**的那组，即 `lr_1e5`（验证集 acc 0.9162）。
**选代表用验证集、评最终用测试集** —— 这是本项目四条路线**统一**的规则：

| 路线 | 变体数 | 按验证集选出的代表 |
|---|---|---|
| TF-IDF | 4 组 n-gram | `char_1_3`（验证集 acc 最高） |
| MacBERT 全参 | 8 组超参 | `lr_1e5`（验证集 acc 0.9162） |
| Qwen3 + LoRA | 4 个秩 | 按验证集选（口径见 `docs/交接清单_提示与LoRA臂.md`） |
| Qwen3 提示 | 3 个变体 | 按验证集选（同上） |

**为什么不能用测试集选？** 用测试集挑代表，等于用最终考场成绩决定谁上场，
测出来的高分会被这个选择本身抬高，后面跟别的路线比就不是公平比较了。
这正是 §5.3(1) 里批评 TF-IDF 那条"测试集更高但没选"时用的同一个道理 ——
**对自己也一样适用**。

这个区别在本项目里不是学术洁癖，而是有具体后果的：
`len512` 的**测试集**最高（0.9281），
但它的**验证集**只有 0.9124，低于代表组的 0.9162。
单看测试集，会选出一个"正式考"分数最高、但"平时练习"水平并不更好的配置。

至于这些差异到底是不是真的，由 §5.3(7) 的配对显著性检验回答：
7 组超参配置与代表组的差异**全部不显著**，
最大 |ΔAccuracy| 只有 0.51 个百分点 ——
**8 组在 777 条测试集上是同一水平，选哪一组都不改变任何结论**。
8 组的完整成绩都在上面的表里，谁高谁低一目了然，**没有藏任何一组**。

> 顺带一个工程上的观察：代表组 `lr_1e5`（学习率 1e-5）训练要 8325 秒，
> 而测试集最高的那组 `len512` 要 12150 秒（长序列）。
> 换句话说，**验证集选出来的那组还便宜了 1.46 倍**。

> **⚠️ 下面用到了两个基准，各管一件事，不要混：**
>
> | 用途 | 用哪一组 | 为什么 |
> |---|---|---|
> | **超参敏感性**（下面三条结论） | `main`（lr=2e-5 / len=256 / 全参 / 3 epoch） | `main` 是实验前定好的标准配置，**除它以外每组只改一个参数**，单变量对比才是干净的 |
> | **路线间对比**（跟 TF-IDF / LoRA / 提示比） | 代表组 `lr_1e5` | 跟别的路线比，要拿各自"最好的那个"来比 |
>
> 其中 `partial` 是唯一**同时改了两个超参**的组合（学习率 2e-5→3e-5 **且** 冻结底部 6 层），
> 所以它与基准的差值只能按"这个组合的整体效果"读，不能归因到某一个超参。
> 这一点在 §5.3(7) 的配对检验里也一样成立 —— 检验回答的是"这两组配置有没有区别"，
> 不是"哪个超参起了作用"。

**结论（可从表中直接读出）**：
学习率在 2e-5 / 5e-5 / 1e-5 三档之间移动时性能变化幅度为 0.52 个百分点量级，
说明学习率**不敏感**，不需要精细搜索；
`partial`（冻结底部 6 层）把可训练参数降到 42.1626%，性能相比全参低0.05；
`len512` 相对 `len256` 的收益是 0.90 个百分点，
说明序列长度**不敏感**，不需要精细搜索——本数据集 P95 长度只有 376 token，截断带来的信息损失本身就不大。

> ⚠️ **上面这些差值都是"表面上"的差值**：在 777 条测试集上，
> 1 个百分点以内的差距未必是真的（单个准确率的标准误约 1.1 个百分点）。
> **这些差异到底是不是真的，由 §5.3(7) 的配对显著性检验（McNemar + 配对 bootstrap）回答**——
> 结论是：超参之间的差异全部不显著，而"TF-IDF → 微调"这个范式差异显著。

> ⚠️ **公平性说明**：8 组配置**全部用同一种组 batch 方式**（长度分桶，见 §4.5），
> 超参、随机种子、样本划分、评测口径完全一致，**组间差异只来自被改动的那个参数**。
> 长度分桶本身是否损失精度，由 §5.3(6) 的对照实验单独回答。

训练样本从 100 条增加到 6210 条，测试集 Accuracy 从
0.8005 变化到 0.9189。这条曲线说明：
在几千条标注数据这个量级上，**数据每翻一倍带来的收益已经在明显收敛**，
这正是"提示/少样本方案有存在空间"的量化依据——
提示臂相当于把训练样本数压到了 4 条（少样本）或 0 条（零样本），
对应的是这条曲线最左端的那个区间。

**但曲线上那些零点几个百分点的起伏，是信号还是噪声？**
777 条测试集上单个准确率的标准误约 1.1 个百分点，所以"2000 条那点比全量高 0.77 个百分点"
这种说法不能直接当真。为此对每个规模点都做了配对检验——
把它和全量（6,210 条）的代表组按 `sample_id` 逐条对齐（方法见 §5.3(7)）：

| 规模点 vs 全量（6,210 条） | ΔAccuracy | McNemar p | bootstrap Δacc 95% CI | 结论 |
|---|---|---|---|---|
| MacBERT n=100 | -12.23 pp | 0.0000 | [-15.06, -9.40] pp | **显著** |
| MacBERT n=1000 | +0.00 pp | 0.8774 | [-1.67, +1.67] pp | 不显著 |
| MacBERT n=2000 | +0.39 pp | 0.7283 | [-1.03, +1.80] pp | 不显著 |
| MacBERT n=3000 | -0.39 pp | 0.7111 | [-1.80, +1.03] pp | 不显著 |
| MacBERT n=500 | -0.26 pp | 0.8774 | [-1.93, +1.29] pp | 不显著 |

→ 与全量存在显著差异的规模点：MacBERT n=100（Δ-12.23pp, p=0.0000）。其余规模点与全量的差异落在评测噪声内。

这条检验的意义在于：**它把"少样本方案有没有生存空间"这个问题从"看起来有"变成了"算过有"。**
如果 100 条和 6,210 条的差距在噪声内，那么"少样本 ≈ 全量"就只是噪声里的错觉，
提示/少样本方案的前提就不成立；反之，两者有可测量的差距，
说明在这个任务上**用提示换标注数据是有代价的**，
而那个代价的具体大小，正是 §5.3(5) 提示臂与 §5.3(4) LoRA 臂要回答的。

| 零样本（只给指令） | 【待补：P_zero_VAL】 | 【待补：P_zero_ACC】 | 【待补：P_zero_MF1】 | 【待补：P_zero_WF1】 | 【待补：P_zero_IFR】 |
| 零样本 + 严格格式约束 | 【待补：P_zero_fmt_VAL】 | 【待补：P_zero_fmt_ACC】 | 【待补：P_zero_fmt_MF1】 | 【待补：P_zero_fmt_WF1】 | 【待补：P_zero_fmt_IFR】 |
| 4-shot 少样本 | 【待补：P_fewshot4_VAL】 | 【待补：P_fewshot4_ACC】 | 【待补：P_fewshot4_MF1】 | 【待补：P_fewshot4_WF1】 | 【待补：P_fewshot4_IFR】 |

> 三个变体的**代表**取验证集 acc 最高的那一个（【待补：P_BEST_NAME】，验证集 【待补：P_BEST_VAL】），
> 与 §5.3(2) 里 TF-IDF / MacBERT 的选法一致；表里三个变体的测试集指标都照实列出，不藏。

**结论**：
- 只加"只输出一个字符"这种格式约束，weighted F1 变化 【待补：CMP_FMT_ZERO】【待补：ABS_FMT_ZERO】 个百分点，
  指令遵循率从 【待补：P_ZERO_IFR】 变到 【待补：P_zero_fmt_IFR】（【待补：P_FMT_DIFR】 个百分点）——【待补：P_FMT_CONC】。
- 从零样本换成 4-shot，weighted F1 变化 【待补：CMP_FEWSHOT_ZERO】【待补：ABS_FEWSHOT_ZERO】 个百分点，
  4 条示例带来的收益 【待补：ABS_FEWSHOT_ZERO】 个百分点，
  与 §5.3(3) 的数据量曲线左端区间**互相印证**。

#### （6）长度分桶 vs 随机组 batch：提速有没有牺牲精度

§4.5 介绍过一个工程优化：把长度相近的评论凑成一个 batch（"长度分桶"），
在本机 CPU 上把训练从约 40 小时压到 24~30 小时（实测吞吐 2.6 样本/秒）。但**工程优化改变了 batch 的组成方式，
有没有偷偷改变结论？** 这组对照专门回答这个问题。

同一份数据（n=1000）、同一套超参、同一个种子，只改组 batch 的方式，各跑一遍：

| 组 batch 方式 | test Accuracy | Macro F1 | 训练耗时 |
|---|---|---|---|
| 长度分桶 | 0.9228 | 0.9119 | 1585 秒 |
| 随机 | 0.9112 | 0.8998 | 2517 秒 |
| **差值（分桶 − 随机）** | **+1.16 个百分点** | +1.21 个百分点 | **-15.5 分钟**（分桶快 1.59 倍） |

**结论**：长度分桶在本机 CPU 上快了 1.59 倍，精度**没有变差**——
分桶的 Accuracy 反而高 +1.16 个百分点，Macro F1 高 +1.21 个百分点。

但这个差值**不能直接当结论用**，得先问它是信号还是噪声。
把两组的 777 条预测按 `sample_id` 逐条对齐做配对检验（方法见 §5.3(7)）：

| 检验 | 结果 | 读法 |
|---|---|---|
| McNemar 精确检验 | b=14 / c=5，p = 0.0636 | 不显著（α=0.05） |
| 配对 bootstrap | ΔAccuracy 95% CI = [+0.13, +2.32] pp | 不跨 0 |
| 两条路线逐条判断 | 一致率 97.6%（19 条判断不同） | 分歧主要来自少数几条 |

→ 两个口径给的是**同一个方向**（分桶略高），但**都停在显著的边缘上**：
McNemar 差一点没到 0.05，bootstrap CI 的下界离 0 只有 0.13 个百分点。

这个结果**够支持**"长度分桶没有牺牲精度"——方向本来就对分桶有利，不需要它来证明什么；
但**不够支持**"分桶比随机组 batch 更好"——那是过度解读。
所以本报告里的用法是：

- 前面 8 组超参配置全部使用同一种分桶方式，**组间比较是公平的**；
- §4.5 的提速可以当作**纯计算量优化**来用（没有任何证据显示它改变了模型学到的结论）；
- 但"分桶比随机组 batch 高 1 个百分点"**不写进任何结论**——它没通过显著性检验。

#### （7）配对显著性检验：上面那些差距，有多少是真的？

**为什么必须做这一步。** 本项目所有路线共用同一份 777 条测试集。
在这么一个样本量上，单个准确率的标准误约 **1.1 个百分点**——
也就是说，一份表里"高 0.8 个百分点"的差距，完全可能只是随机波动。
只比汇总数字，很容易把噪声写成"某个超参更好"的结论，这在评审时一问就穿。

**方法。** 把两条路线的 777 条预测按 `sample_id` 逐条对齐（不是比两个汇总数，
而是比**同一条样本上的对错差异**），然后用两种互补的配对检验：

| 方法 | 回答什么问题 | 实现 |
|---|---|---|
| McNemar 精确检验 | 两条路线"谁对谁错"的不一致对里，差异是否显著 | 双侧精确二项检验；不一致对 ≤40 时用精确二项和，>40 时用正态近似 |
| 配对 bootstrap（10,000 次） | 指标差值的 95% 置信区间跨不跨 0 | 对测试集重采样，每次同时算两条路线的指标差，取 2.5% / 97.5% 分位 |

两者都实现在 `src/eval/evaluate.py`，批量跑在 `src/eval/paired_tests.py`，
原始输出 `src/results/paired_tests.csv`（每行一组配对）、`paired_tests.md`（下表）、`paired_tests_key.json`。

   McNemar 不一致对 b=21 / c=51，
   p = 0.0006，显著（α=0.05），
   bootstrap 95% CI [-6.05, -1.80] 不跨 0。
   而另外 7 组超参配置（学习率 / 类别加权 / 冻结层数 / 序列长度 / 训练轮数）
   与代表组 `lr_1e5` 的差异全部不显著，
   最大 |ΔAccuracy| 只有 0.51 个百分点（MacBERT len512 vs MacBERT lr_1e5），
   McNemar p 值范围 0.5966 ~ 1.0000，置信区间全部跨 0。
   → **在这个数据规模上，超参的影响小于评测噪声；真正拉开差距的是"用不用微调"，不是"微调用哪组超参"。**
   这条结论如果只比汇总数字是得出来的——`len128` 表面高 0.77 个百分点，
   看上去像是"短序列更好"，但配对检验说明那只是这一份测试集上的随机波动，
   **不能写成结论**。

2. **对 LoRA 臂的直接含义**：既然冻结底部 6 层、只训 42% 参数的 `partial`
   与全参微调的差异也不显著，那么"参数高效微调会不会掉点"这个问题，
   在本任务上的答案很可能是"不会显著掉点"——同学那条 LoRA 臂的绝对分数
   应当与 MacBERT 全参处于同一量级，而差距主要来自底座模型规模（1.7B vs 102M）而非参数效率。

> ⚠️ **这个检验能说明什么、不能说明什么**：
> 显著 = 在这 777 条样本上，"这个方向不是偶然"的证据足够强；
> 不显著 = 现有样本量不足以区分，**不等于两者相等**，只等于"不能断言有差别"。
> 要把某个 0.5 个百分点的差异做成结论，需要把测试集扩到几千条，
> 或者对同一配置做多种子重复实验——这两件都超出了本次作业的预算，
> 所以本项目选择**如实报告不显著**，而不是硬凑一个结论。

### 5.4 总体结论

- **准确率排序**：MacBERT 全参（lr_1e5） 最好。
- **成本排序（从低到高）**：提示（0 训练成本，付费推理）→ TF-IDF（0 训练成本，秒级 CPU）→
  LoRA（训练 【待补：LORA_PARAMS】 参数）→ MacBERT 全参（训练 102,269,186 参数）。
- **一句话**：在这个任务上，**提示和微调之间的准确率差距（【待补：ABS_LORA_PROMPT】 个百分点的
  weighted F1）远小于两者之间的成本差距**。
  如果目标只是"上线一个能用的情感分类器且手上没有标注数据"，提示路线是成立的；
  如果目标是"要准、且愿意标注几千条数据"，全参微调是明确的更优解。

| 领域覆盖 | 单一领域（携程酒店评论），且集中在 2010 年前后 | 换到餐饮、外卖、直播带货等语料，绝对分数不可迁移 |
| 标签质量 | 二分类且来源是原始评分聚合，**否定和转折**天然有歧义 | 上限本身被标签噪声压住，这是所有路线共同的"天花板" |
| 类别不均衡 | 负面仅占 31.5% | 单看 Accuracy 会严重高估；必须同时看 Macro F1 |
| 成本 | 提示臂单条 【待补：LAT_MEAN】 ms，777 条测试集约 【待补：LAT_TOTAL_MIN】 分钟 | 批量场景下提示臂的推理成本是真实负担；微调后模型可以走批处理 |
| 延迟 | 提示臂 P95 【待补：LAT_P95】 ms | 交互式场景可接受，实时风控场景需要异步化 |
| 隐私与合规 | 评论正文含用户 ID、日期、酒店名等字段 | 本项目**不把评论正文放进提交包**，只提交 ID 清单与统计数字；原始数据只在 Kaggle session 内使用 |
| 数据许可 | 上游只有模板式 Apache-2.0 标记，评论正文再分发权利未经核实 | 不建公开 Dataset，只用 `Add Input → Upload` 在 session 内使用 |

## ⑦ 工程与伦理

### 7.1 成本与延迟

| 路线 | 训练成本 | 推理成本（单条） | 延迟测量环境 |
|---|---|---|---|
| TF-IDF | 无（sklearn 秒级） | 0.7 ms（batch=1，200 条冻结样本，P50 0.6 / P95 1.2） | 本机 CPU，12 线程（WSL / sklearn 1.9.1） |
| MacBERT 全参 | 8 组配置约 45 分钟（单卡 T4），本机 CPU 实测 24~30 小时 | 103.5 ms（batch=1，同一批样本，P50 81.0 / P95 207.4） | 本机 CPU，12 线程（Windows / torch 2.10.0+cpu） |
| Qwen3 提示 | **0**（不训练） | 【待补：LAT_MEAN】 ms（batch=1），平均 【待补：LAT_TOK】 prompt token | Kaggle T4 GPU（fp16） |
| Qwen3 + LoRA | 约 50 分钟（单卡 T4），只更新 【待补：LORA_PARAMS】 参数 | 【待补：LoRA 延迟】 ms（batch=1，同一批样本，P50 【待补：LoRA 延迟】 / P95 【待补：LoRA 延迟】） | Kaggle T4 GPU（fp16） |

> **四条路线用同一套协议测延迟**：同一批 200 条冻结样本（`latency_ids.json`）、
> `batch=1` 逐条推理、预热 20 次后开始计时。
> MacBERT 那一臂是在**训练进程退出、机器空闲**时测的 —— 中途在训练占满 CPU 时测过一轮，
> 数字被抢走的算力抬高了近两个数量级（219.8 ms/条），那种数字没有比较意义，故作废。

> ⚠️ **横向比较只在同硬件内成立**：前两行是**本机 CPU**，后两行是 **Kaggle T4 GPU**。
> GPU 的单条延迟天然比 CPU 低一个数量级，**这两组数字不能直接相减**。
> 能横向相减的是两两同环境的两组：
> ① **TF-IDF vs MacBERT**（都在本机 CPU，实测差 **148 倍**），
> 这是"传统方法 vs 深度学习"的推理成本代价；
> ② **提示 vs LoRA**（都在 T4、同一底座同一模型：提示是 `generate` 逐字生成，
> LoRA 是分类模型的一次 forward；LoRA 多挂一个 adapter，额外开销很小，
> 实测是提示臂的 **【待补：LAT_LORA_OVER_PROMPT】 倍**），
> 这是"要不要训练"之外的另一个维度。
>
> 换句话说：**本项目能把成本讲清楚，靠的是把"训练成本"和"推理成本"分开算，
> 而不是把所有延迟数字塞进一个表里直接比大小。**

### 7.2 权限与隐私

- 原始评论中包含用户昵称、评论日期、酒店名称等可能构成个人信息的字段。

- 提交包内**只含**：源码、配置、ID 清单（不含量表外的信息）、统计数字、报告、图表。
  **不含**：模型权重、checkpoint、录屏、数据集、虚拟环境、任何 API Key。
- **评论正文的处理**：逐条预测文件（`predictions_*.csv`）只保留 `sample_id`、标签和概率，
  **不带正文**；全部错误样本清单（`errors_by_class.csv`）同样只带 `sample_id`。
  全项目只有报告 §6.1 直接引用的 **3 条**样例（`error_samples.csv`）带正文，
  其余任何评论正文都不进提交包——这也是 §7.3 数据许可判断的落地方式。

### 7.4 AI 使用声明

**使用的工具**：Claude Code（Anthropic 的编程助手，本地运行）。

**用在哪些环节**：

| 环节 | AI 的具体参与 | 人工/本项目做了什么 |
|---|---|---|
| 写代码 | 起草 5 个训练脚本、结果汇总脚本、报告模板 | 逐行阅读并按本机/Kaggle 实际报错修改；所有脚本在真机上跑过 |
| 调试 | 阅读 transformers / peft 源码定位 Qwen3 的 `pad_token_id` 与扁平 config 问题；定位 fp16 + AdamW `eps` 下溢 | 判断"这个改动是否值得做"并决定最终修法 |
| 数据处理 | 写清洗/划分脚本 | 核对统计数字（7,766 = 7,763 + 1 + 2）与上游字段说明，确认标签 0/1 的语义不是猜的 |
| 写作 | 生成报告骨架、README、摘要初稿 | **实验设计、指标口径、结果解读、结论由学生负责**；AI 写出的每个数字都由脚本从 CSV 读出，不手写 |
| 评估 | 写 `collect_results.py` / `fill_report.py` 做数字归集 | 决定"weighted F1 必须按测试集真实标签数加权"这个口径问题 |

**如何验证 AI 的输出**：
1. 所有 AI 写的代码都在真机（Kaggle T4 / 本机 CPU）上**跑通过**，不是纸面代码；
2. 报告中的每个数字都由 `fill_report.py` 从各路线产出的 CSV/TXT **直接读取**，
   人工无法手改，杜绝"编造实验数据"；
3. 涉及 transformers 行为的判断（Qwen3 的 pooling 位置、thinking 模式、padding 方向）
   均通过**阅读库源码 + 对照实际输出**双重确认，不凭记忆下结论；
4. AI 给出的任何"数字"若无法在输出文件中找到出处，一律不写进报告。

**人工修改的部分**：全部实验方案（8 组超参、3 个提示变体、4 个 LoRA 秩、5 点数据量曲线）
由学生确定；报告的结论句、失败样例的语义归因、局限判断由学生撰写；
AI 生成的代码在合并前逐段审阅并按实际报错修正。

**未使用 AI 生成任何实验数据、日志或截图。**
