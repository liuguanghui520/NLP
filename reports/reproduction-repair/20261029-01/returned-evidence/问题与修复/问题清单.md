# 问题与修复建议

以下问题按“已确认证据”和“建议”分开。没有把未执行到的后续依赖错误说成模型运行错误。

## P0：CUDA 驱动低于锁定 PyTorch cu130 要求

**触发命令与阶段**

```text
python src/run.py \
  --models \
  --paths src/project/configs/reproduce-models.local.json \
  --work-dir "/mnt/d/NLPP/reproduction-runs/L2-attempt-001-20261029T1648"
```

阶段是 `src/model_reproduction.py` 导入 torch 后、`prepare()` 之前、任何模型加载与任何 777 条测试预测之前。

**原始错误与位置**

```text
CUDA initialization: The NVIDIA driver on your system is too old
(found version 12020).
...
RuntimeError: The full suite requires CUDA with BF16 support;
no precision/model substitution is made
```

- `命令与原始日志/04_第二层模型重新预测/失败运行-L2-attempt-001/model-stderr.log`
- `.../results-model-reproduction/status.json`
- `.../submission-status.json`
- `文件身份与环境/locked-model-env-probe.stderr.log`

**原因与证据**

- 本机 NVIDIA 驱动 537.70，`nvidia-smi` 报告 CUDA 12.2；错误中的 `12020` 对应驱动 API 12.2。
- 锁定的 PyTorch 2.14.1 实际是 `+cu130`，需要支持 CUDA 13.0 的驱动。
- 实际探测为 `cuda_available=False`、`cuda_bf16_supported=False`。
- 提交包环境 E01 自述使用驱动 616.92、CUDA UMD 13.4，原机与本机驱动条件不同。

**建议的最小修复**

1. 从 GPU/整机厂商获取并安装支持 CUDA 13.0 的正式 Windows NVIDIA 驱动，优先核对 E01 记录的 616.92 或更新兼容版本。
2. 重启后运行 `nvidia-smi`、`文件身份与环境/verify_locked_model_env.py`，确认 CUDA 可用且 BF16 小张量可执行。
3. 在全新 `L2-attempt-002-*` 工作目录重跑完整 11 模型命令。

不要为了规避该错误静默把 torch 降到 2.5.1，也不要切到 CPU、FP16 或量化。现有 LLaMA-Factory `.venv` 的 torch 2.5.1 只能作为工具可用性证据，不能冒充锁定环境。

**实验条件与主结果影响**

驱动升级不改变模型、数据、提示、精度或指标算法；但未完成 11 次运行前不能给出新机主结果。若改 torch/CUDA 构建，需另立环境差异并重跑全部方案。

**修复后的验证**

先用 `verify_locked_model_env.py` 通过，再执行同一 `--models` 命令；验收仍是 11 运行各 777 条、`results/model-reproduction/status.json` 为 `passed`、指标差不超过 `1e-12`。

## P1：LLaMA-Factory 依赖未完整锁定

**触发与证据**

新 venv 已安装 README 指定依赖，但验证导入 `llamafactory.chat.ChatModel` 时：

```text
ModuleNotFoundError: No module named 'datasets'
```

日志：`文件身份与环境/llamafactory-import.*`。此外新环境实际安装了 `accelerate==1.15.0`，而本机 LLaMA-Factory 0.9.6.dev0 的 `pyproject.toml` 要求 `accelerate<=1.11.0`。现有 Factory `.venv` 有 `datasets==4.0.0`、`accelerate==1.11.0`，其 `ChatModel` 导入通过，但 torch 是 2.5.1+cu121，不符合提交锁定版本。

README 把它称作“完整快照”的 `requirements.integration.lock` 实际仅列出 10 个直接项目；新环境最终解析出 73 个包。该文档/锁文件不足以复建可导入 Factory 的环境。

**建议修改**

- 文件：`src/project/requirements.integration.lock`，以及 README 中的“完整快照”表述。
- 最小内容：从实际 E01 模型环境生成完整 `uv pip freeze`；至少约束 LLaMA-Factory 所需的 `accelerate==1.11.0`、`datasets==4.0.0`、`trl`、`torchdata`、`sentencepiece`、`modelscope` 等，并记录 LLaMA-Factory commit。
- 修复环境后执行 `uv pip check`、`from llamafactory.chat import ChatModel`，再跑全部 11 个模型。

**实验条件影响**

这是运行时依赖兼容性修复，不改变方法定义；但任何依赖集合调整都可能影响数值，必须全量重跑并重新比较，不能复用旧参考值宣称通过。

## P1：MacBERT seed42 训练产物镜像拼接哈希不一致

**触发与证据**

- 期望 archive SHA256：`bbb9001a10d1e7603ae43311dd9827fc1e092b8194268f70c448a0aa3c448268`。
- 镜像分段拼包实际 SHA256：`49d6d6e4b9544971fa3232d78e6e6d9ce442bc6e3edb20bc8b9e957797f345b5`。
- 实际大小正确：381,052,561 bytes。
- `python -m zipfile -t` 在 `bert-len512-seed42/model/model.safetensors` 解压时报 `invalid code lengths set`。

证据：

- `命令与原始日志/04_第二层模型重新预测/segmented-downloads/bert-len512-seed42.zip.integration-attempt-001.status.json`
- `问题与修复/bert-seed42-integrated-attempt-001-zip-test.log`
- `问题与修复/bert-seed42-corrupt-offset-diagnostic.log`

镜像的一个 31.76MB 分段被重新取得后哈希相同；其第 3 段又与官方 Range 请求逐字节一致。因此当前尚未把损坏定位到单一原始分段，不能用该拼包。

**建议修改**

不修改模型代码。删除/隔离该失败资源仅指不把它作为正式输入；在证据中保留原失败文件。重新从官方 Release 下载完整的 `bert-len512-seed42.zip`，先校验 archive SHA256，再保存 ZIP CRC/成员校验结果，才可解压。

**实验条件与结果影响**

文件身份修复不改变实验条件；只有发布资产原始字节与锁定 SHA256 一致时才可继续。不得改 manifest 或参考成绩消除差异。

## P2：Windows `safe_path` 兼容性

**触发与证据**

原始第 2 次运行在并发下载阶段报：

```text
ValueError: Path outside working directory:
data/processed/v1-20261023/alpaca/test.json
```

失败目录：`D:\NLPP\reproduction-runs\L1-attempt-002-20261029T1544`。事后逐项复检同一路径时 `is_relative_to()` 又为真，说明 Windows 并发写入期间的目标路径动态 `resolve()` 边界判断不稳定。原始失败输出仍保留。

**最小补丁**

文件：`src/project/submission_reproduce.py` 的 `safe_path()`。

- 拒绝绝对路径、盘符、根锚点和 `..` 路径段。
- 用 `root.resolve().joinpath(*name.parts)` 构造目标，不在文件刚创建时依赖目标 `resolve()` 后的字符串比较。

前后源码与补丁：`submission_reproduce.before.py`、`submission_reproduce.after-all-compatibility-patches.py`、`提交包工程兼容补丁-clean.patch`。干净补丁已在原文件副本上通过 `git apply --check`；路径逻辑也通过绝对路径、盘符和 `..` 拒绝测试。

**实验条件与结果影响**

只改变输入路径校验实现，不改变读取/下载内容；第 9 次仍逐文件校验 SHA256，第一层指标差为 0。

**验证**

第 9 次第一层运行退出码 0，47/47 输入哈希匹配，16 份记录和 11×777 测试预测均完整。

## P2：GitHub raw 大文件传输失败；已加同身份镜像回退

**触发与证据**

- 直连固定提交 `raw.githubusercontent.com` 对较大 JSON/预测反复出现 `WinError 10054`。
- GitHub Contents API 在一次大文件尾部出现 `IncompleteRead(642468/651110)`，并发时出现 403。
- ghfast 镜像多数成功，但一份文件曾 504/连接超时；改用同一固定提交的直连回退后第一层成功。

证据：所有 `attempt-001` 至 `attempt-008` 的 runner 日志与外层失败 JSON。

**最小补丁**

Windows/Linux 均先使用固定提交 `106cdbed...` 的镜像 URL，失败后回退固定提交的官方 raw URL；客户端使用 `curl`，每次读取完整响应后先校验 `input-sha256.json` 中的 SHA256，才写正式目标。输入下载改为串行，避免镜像/API 限流。

补丁不替换数据版本；镜像只是传输层。对长期工程，建议改为可配置的已验证本地输入缓存，而不要把第三方镜像硬编码为主路径。

**实验条件与结果影响**

网络与路径变化不改变数据字节或模型协议。所有 47 个文件均在落盘前/使用前执行锁定哈希检查。

## P2：外层错误信息把“失败”和“完成但有差异”混为一谈

**触发与证据**

`submission_reproduce.py` 对模型子进程只要返回非零就写成：

```text
Real-model reproduction failed or differs from reference
```

本次外层状态为 `failed`，而内层清楚地记录 `failed`、`completed=[]` 和 CUDA 错误，并不是完成后的指标差异。

**建议修改**

文件：`src/project/submission_reproduce.py`，模型子进程返回后的错误分支。读取 `results/model-reproduction/status.json`：

- `failed`：外层记录具体失败信息。
- `completed_with_differences`：外层保留完成数、最大差和差值状态。

**影响**

只改状态诊断，不改模型、预测或指标；修复后重跑第二层验证。
