## 2. 当前分支处理顺序

1. **保护现状。** 确认正式工作副本路径、分支及未提交修改；如有修改先辨明来源并保存。为现有项目分支建立本地保护分支`codex/archive-before-integration-20261028`，记录起点提交。保护分支不自动推送，不因做了备份就绕过公开内容检查。
2. **核对远程。** 获取远程分支信息，确认origin/main与codex/data-processing-v1的关系，以及相关提交是否已推送或合并。
3. **建立融合分支。** 从最新origin/main创建`codex/integration`。若同名分支已存在，先核对用途并继续合适分支，不强制重置。
4. **纳入旧项目历史。** 旧项目提交已是main祖先时不重复导入；尚未合入时正常合并旧分支。若远程旧分支有本地尚未获取的有效提交，先核对再纳入。不得以整边覆盖方式丢弃课程材料或队友代码。
5. **保留旧分支。** 本阶段不删除codex/data-processing-v1，新增融合工作进入codex/integration。
6. **推送并建立草稿PR。** 审阅可公开内容后推送融合分支，设置跟踪关系，建立指向main的草稿PR。草稿PR不表示实验已经完成。

目标关系：

```text
已有main历史
    └── codex/integration
         ├── 旧项目分支尚未合入的历史
         ├── 成员交付接收
         ├── 公共接口统一
         ├── 各路线适配
         ├── 实验与评估记录
         └── 文档与独立复现验收
                  ↓
                main
                  ↓
           最终提交版本标签
```

不在当前无提交的master另起一套完整历史再覆盖远程。长期协作使用同一个仓库，各成员自行克隆；如以后调整正式工作副本位置，采用保留历史的克隆/迁移方式，并更新路径说明，不重新初始化替代。

## 3. 每次提交的共同要求

- 一个提交对应一个真实完成、可检查的功能或证据单元，不按文件数量机械拆分。
- 提交前检查暂存差异、敏感信息、文件大小和实际完成状态；不用未经审阅的全目录暂存代替检查。
- 不提交密钥、虚拟环境、缓存、模型权重、批量检查点、个人路径配置及无权公开的数据正文。
- 完整运行日志保留本地或可访问的外部归档；仓库提交可公开摘要、清单、校验和及获取说明。含评论原文的日志、错例和预测同样受发布条件约束。
- 代码提交说明写明修改目的和已完成检查；没有运行的检查明确写未执行。
- 训练前尽量先提交实际使用的代码，并将提交号记入运行manifest；工作区有未提交差异时额外记录dirty状态和源码哈希，不能假称纯净提交。
- 旧成果不覆盖，新结果使用独立run_id。需要修复时新增提交及关联运行，不倒改旧日志。

## 7. 阶段四：正式实验、结果与冻结

源码修改与实验结果分开提交，训练运行关联已经提交的代码。

| 建议提交标题 | 内容 |
|---|---|
| `results: record validation searches and selected configurations` | 参数搜索索引、验证指标、配置哈希、最佳检查点映射和失败记录 |
| `results: record three-seed experiments and evaluation freeze` | 42/43/44结果、产物清单、一致性核验及最终冻结清单 |
| `results: add final evaluation and benchmark summaries` | 最终测试、正式延迟、独立重算与资源成本摘要 |

训练期间发现错误时：保留失败运行 → 单独提交修复 → 新建run_id → 记录父运行和新旧代码提交号 → 重新核验受影响结果。

模型、适配器、Pipeline、检查点和完整日志不因需要Git证据就全部塞入仓库。提供校验和及可访问链接，并明确链接是否需要权限。未知或尚未上传的资源不能写成已公开可用。

## 8. 阶段五：分析、图表与报告

| 建议提交标题 | 内容 |
|---|---|
| `feat: export cross-method errors and comparison figures` | 错例、共同失败/修正/退化、统一结果表与绘图工具 |
| `docs: add verified analysis and project report` | 人工审阅的错误归因、局限、成本解释、报告、贡献与AI声明 |

至少3类错误归因、3个真实失败案例。图表标注数据来源、运行、坐标轴及单位；结果变化时同步更新表图，不手工修改图上数字凑一致。结果解释由学生本人完成，AI辅助范围如实声明。

## 9. 阶段六：复现验收与最终发布

| 建议提交标题 | 内容 |
|---|---|
| `docs: add clean-machine reproduction instructions` | 主README、已验证环境、资源获取、完整命令、预计耗时及故障处理 |
| `test: record independent reproduction acceptance` | 新机环境、实际命令、日志索引、结果核对及限制 |
| `release: prepare final course submission` | 最终清单、大小检查、外链、摘要、演示与版本说明 |

新机失败先提交修复，再重验受影响步骤。未实际完成不能写复现通过。区分使用已有模型推理、已有预测重算及重新训练三种验收，不以查看旧结果表替代真实模型运行。

## 10. 三人任务分支与协作

从最新codex/integration建立对应任务分支：

| 分支 | 主要内容 |
|---|---|
| `codex/baseline-macro-f1` | BERT、TF-IDF修改及证据整理 |
| `codex/prompt-evaluation` | 提示适配、公共评估、错例输出 |
| `codex/lora-evidence` | LoRA产物索引、配置和资源核验 |

分支名称表示任务，不自动改变既有三人职责；具体执行者按实际分工填写。每人使用本人的Git身份，不共用账号冒充贡献。

- 各任务通过小型PR合入codex/integration，优先保留有意义的原始提交，不把全项目压成一个最终提交。
- 不并行修改同一公共协议；协议变更先达成一致，提交后通知各成员更新。
- 使用不同分支不代表在同一工作目录可同时安全切换；多人各自克隆，或使用彼此独立的工作副本。
- 收到队友更新后正常合并，不强制重写别人已共享的历史。
- 每个PR写清问题、改动、检查、结果证据及未完成项。实验完成状态以真实运行证据为准。

## 11. 合并main与版本标签

融合分支经审阅和验收后，通过PR合入main。不要在未完成阶段以正式发布标题掩盖缺失项。

- 不强制推送覆盖main，不删除课程材料及队友历史。
- 最终通过版本建立标签，例如`course-submission-v1`。
- 提交包记录标签及完整提交号；标签指向的源码应包含对应最终README、配置和证据索引。
- 打包说明通过外部清单关联产物和提交号，不为把自身提交号写进同一提交而制造循环记录。
- 后续修复新增提交和`course-submission-v1.1`等新标签，不移动旧标签掩盖变更。
- 最终确认PR已合并、main及标签已推送、外链可访问；本地存在不等于GitHub已可见。
