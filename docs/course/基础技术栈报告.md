# 自然语言处理课程项目基础技术栈报告

编写日期：2026-10-18  
项目方向：C 提示 vs 微调对比  
文档用途：明确基础技术选型、辅助工具、运行方式及可复现要求，作为后续开发的参考。

## 1 项目定位与选型结论

本项目围绕同一 NLP 任务，比较非大模型基线、零样本提示、少样本提示和 LoRA 微调方案，重点关注分类效果、运行成本、延迟与失败案例。

当前建议以**中文评论情感分类**作为候选主题：输入一段中文评论，输出正向或负向标签。该任务输入输出明确，便于统一评价和展示难例。中文新闻分类可作为备选主题。最终主题与数据版本尚待小组确认。

建议采用以下基础组合：

- 核心开发：Python、PyTorch、Transformers、PEFT。
- 传统基线：scikit-learn，实现 TF-IDF＋LinearSVC。
- 自动调参：传统基线使用 RandomizedSearchCV；LoRA 按算力预算使用 Optuna。
- 训练监控：TensorBoard。
- 数据与结果：pandas、JSONL / CSV、Matplotlib。
- 可复现管理：Git、配置文件、依赖版本文件、真实运行日志。
- 演示：按需要增加 Gradio。

以上为拟采用技术，不代表已经安装、配置或验证通过。

## 2 核心技术栈

| 层次 | 推荐技术 | 主要职责 | 选型说明 |
| --- | --- | --- | --- |
| 开发语言 | Python 3.11 | 统一数据处理、训练、推理和评估 | 作为拟定项目环境；落地时核验依赖兼容性 |
| 数据处理 | pandas、Python 标准库 | 读取、清洗、去重、检查标签、保存数据清单 | 保留样本编号，方便追踪预测和错误案例 |
| 数据格式 | JSONL / CSV | 保存样本、划分清单和逐条预测 | 便于脚本处理和人工检查 |
| 传统基线 | scikit-learn | TF-IDF 特征提取与 LinearSVC 分类 | 计算成本较低，适合本机运行 |
| 深度学习框架 | PyTorch | 张量计算、模型训练与设备管理 | 与 Transformers、PEFT 共用训练流程 |
| 模型加载与推理 | Transformers | 分词、聊天模板、模型加载、生成和训练入口 | 提示与微调尽量采用相同的处理流程 |
| 参数高效微调 | PEFT | 配置 LoRA、训练适配器、保存和加载适配器 | 降低可训练参数量；实际显存需求需测量 |
| 指标计算 | scikit-learn | Accuracy、Precision、Recall、F1、混淆矩阵 | 统一各方法的指标口径 |
| 图表输出 | Matplotlib | 绘制结果对比、混淆矩阵和日志曲线 | 报告图表从真实结果文件生成 |

TF-IDF 是特征表示方法，需要与分类器组合后才能完成分类。scikit-learn 提供相应特征提取接口，支持配置分析器和 n-gram 等参数。[官方文档](https://scikit-learn.org/1.7/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html)

PEFT 可在冻结基础模型参数的同时添加和训练 LoRA 参数，并单独保存适配器。需要注意，LoRA 减少了可训练参数，但基础模型仍需参与前向计算和反向传播中的相关计算。[官方文档](https://huggingface.co/docs/peft/en/quicktour)

## 3 数据集与模型候选

### 3.1 数据集

| 候选数据集 | 对应主题 | 适用理由 | 使用前需要核对 |
| --- | --- | --- | --- |
| ChnSentiCorp | 中文评论情感分类 | 标签明确，便于开展分类对比和分析否定、转折、褒贬混合等样例 | 具体版本、标签含义、数据划分、许可和重复样本 |
| THUCNews | 中文新闻分类 | 多分类任务，便于观察类别间混淆 | 具体版本、类别范围、文本长度、类别分布和许可 |

PaddleNLP 官方文档提供这两类数据集的读取入口，可作为定位数据的参考；项目仍可将核验后的数据转换为统一格式，使用 PyTorch 进行训练，无须因此同时引入 PaddlePaddle 训练框架。[数据集文档](https://paddlenlp.readthedocs.io/zh/latest/data_prepare/dataset_list.html)

原始数据应保留来源说明，清洗后的数据应保留处理规则与划分清单。数据集和模型权重按任务书要求通过链接提供，不放入最终提交压缩包。

### 3.2 模型

首选候选为 **Qwen2.5-1.5B-Instruct**，用于零样本提示、少样本提示及 LoRA 微调。该模型提供官方 Transformers 使用示例，模型卡标示采用 Apache 2.0 许可。[模型说明](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct)

算力进一步受限时，可评估 **Qwen3-0.6B**。该模型支持通过 `enable_thinking=False` 关闭思考模式，便于控制分类任务的输出形式与生成长度。[模型说明](https://huggingface.co/Qwen/Qwen3-0.6B)

模型选择以小规模运行验证为依据。选定后，应记录完整模型标识和具体 revision，提示与微调共用同一基础检查点。暂不预设哪种方法效果最好。

## 4 调参工具

### 4.1 传统基线调参

建议使用 scikit-learn 的 **RandomizedSearchCV**；搜索范围较小时也可以使用 **GridSearchCV**。

工具可用于选择 TF-IDF 的字符或词特征、n-gram 范围、词表大小，以及 LinearSVC 的正则化参数 `C`。使用交叉验证时，应将特征提取与分类器放入同一个 Pipeline，使每一折的词表与 IDF 仅从该折训练数据拟合，避免数据泄漏。[参数搜索文档](https://scikit-learn.org/stable/modules/grid_search.html)

### 4.2 LoRA 自动调参

建议按需使用 **Optuna**。它支持定义搜索空间、根据历史试验选择后续参数、提前终止表现不佳的试验，并生成搜索历史等图表。[官方文档](https://optuna.readthedocs.io/en/stable/)

可以纳入工具配置的参数包括学习率、LoRA 秩 `r`、dropout 和训练轮数。实际搜索范围、试验次数和评价目标由小组结合算力及课程要求确定。

Transformers 的 Trainer 提供超参数搜索接口，可连接 Optuna。涉及 LoRA 结构变化时，可使用自定义试验函数完成模型与适配器构建。每次试验必须从相同基础检查点重新初始化模型和适配器。[集成说明](https://huggingface.co/docs/transformers/en/hpo_train)

可选增加 **Optuna Dashboard**，查看试验列表、搜索历史和参数重要性。参数重要性是对既定搜索范围与已完成试验的分析，不能直接当作参数影响的因果结论。[Dashboard 说明](https://optuna.readthedocs.io/en/stable/#web-dashboard)

### 4.3 提示方法的配置管理

提示模板、示例数量和示例选择方式可通过配置文件管理，并由统一评估脚本执行。初期使用简单批处理即可，无须单独引入自动提示优化框架。

调参依据来自验证集或训练集内部的交叉验证。测试集不参与参数选择、提示修改或示例筛选，最终配置确定后再用于评价。

## 5 训练监控与实验记录

| 工具或文件 | 用途 | 当前建议 |
| --- | --- | --- |
| TensorBoard | 查看训练 loss、验证指标和学习率随训练进度的变化 | 基础方案中采用 |
| CSV / JSON 结果文件 | 汇总方法、参数、指标、耗时等字段 | 必须保留，便于复核与生成图表 |
| JSONL 逐条预测文件 | 记录样本编号、真实标签、原始输出、解析标签和错误信息 | 必须保留，支撑错误分析 |
| MLflow | 统一记录参数、指标、代码版本及输出文件 | 多人协作、试验较多时增加 |
| Ray Tune | 调度较大规模的调参任务 | 有多 GPU 或多机器需求后再评估 |

PyTorch 提供 TensorBoard 的写入接口，可记录标量等数据；MLflow 提供实验追踪 API 和界面；Ray Tune 提供超参数调优与任务调度能力。[TensorBoard 文档](https://docs.pytorch.org/docs/2.14/tensorboard.html)、[MLflow 文档](https://mlflow.org/docs/latest/ml/tracking/)、[Ray Tune 文档](https://docs.ray.io/en/latest/tune/index.html)

每次运行至少保留以下信息：运行编号、执行命令、代码版本、数据版本与划分、模型 revision、参数配置、随机种子、软件与硬件环境、指标、耗时及逐条预测结果。报告中的关键数字应能追溯到这些记录。

分类任务除主要指标外，还应记录无法解析为合法标签的输出。解析规则须固定，并明确这类输出如何计入指标，不能无说明地删除样本。

## 6 运行环境与资源安排

前期设备检查检测到 AMD Radeon 780M 核显，未检测到 NVIDIA 显卡。基于当前检测结果，建议采用以下分工：

| 运行位置 | 建议承担的工作 |
| --- | --- |
| 本机 | 数据处理、传统基线及其调参、结果分析、报告图表和演示界面开发 |
| 学校 GPU 服务器或云端 GPU | 大模型批量推理、LoRA 训练和受预算限制的调参 |

CPU 可用于小规模运行验证，但训练与批量推理耗时需要实测。云端资源尚未确定，不在本报告中承诺训练时长、显存占用或费用。

开展自动调参前，应先验证一组配置能够完整运行，记录单次耗时与资源占用，再设置搜索次数或总时长上限。工具不会消除重复训练带来的成本。

## 7 演示与工程组织

演示界面可使用 Gradio，提供评论输入、方法选择、预测标签及运行耗时展示。界面调用统一推理模块，批量评估也调用该模块，保持结果口径一致。

建议后续采用以下目录结构；目前仅为组织建议，不表示相关模块已经实现。

```text
NLP_assignment/
├── doc/                   # 任务要求、技术报告及后续说明
├── configs/               # 数据、提示、模型与训练配置
├── src/
│   ├── data/              # 读取、清洗和划分检查
│   ├── baseline/          # TF-IDF 与分类器
│   ├── prompting/         # 提示构造与标签解析
│   ├── finetuning/        # LoRA 训练与适配器加载
│   ├── evaluation/        # 统一指标与逐条预测保存
│   └── demo/              # 演示入口
├── outputs/               # 结果表、预测文件与图表
├── logs/                  # 日志与训练监控记录
├── README.md              # 环境、运行命令和预期输出
└── requirements.txt       # 验证通过后的依赖版本
```

依赖版本应在训练与推理流程验证通过后固定。GPU 环境另行记录驱动、CUDA 和 PyTorch 构建版本，不能仅依靠一份依赖列表说明全部环境。
